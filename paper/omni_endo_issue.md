# Data correctness issues in the generated prompt, and a note on LLM answer variability

Thanks for building and open-sourcing this. I have been studying a closely related workflow (a tool that packages AndroidAPS/Nightscout data and hands it to a user-chosen LLM for a settings review, replayed 490 times across eleven models), so I read `public/index.html` and `server.js` with that in mind. Two kinds of findings below: concrete correctness issues in the prompt generation, and a design consideration about LLM variability that our data speaks to directly.

## Correctness issues in the generated prompt

1. Units are hard-coded as mmol/L regardless of the account's units. `formatHeader` prints `${sn.value}mmol/L` for targets and `1U:${sn.value}mmol/L` for ISF (index.html ~lines 629-631), and the average BG line is labelled mmol/L, but the values come straight from Glooko in whatever unit the account uses. The GMI formula (`3.31 + 0.02392 * (avg * 18.0182)`, ~line 612) also assumes mmol input; for an mg/dL account it returns a wildly wrong estimated A1c. The `unitToggle` only converts the user-typed hypo/hyper thresholds (~line 451), so an mg/dL user gets a prompt whose numbers and labels disagree throughout. Suggest detecting the account unit from the Glooko payload and converting or labelling consistently.

2. The deep-dive Timeline export contains no basal delivery, but is described as "best for analyzing overnight stability and long-term basal efficacy". `server.js` requests only `cgmHigh`, `cgmLow`, `cgmNormal` and `deliveredBolus` series, so the granular export the AI is asked to audit basal efficacy from has no basal data in it. In our study the equivalent omission (a bolus-only insulin total with no basal delivery in the package) led the most-used model to treat the bolus sum as TDD in 49 of 50 conversations and to recommend cutting safety limits on that arithmetic; whether a model notices an omission like this is essentially random. Glooko's graph API exposes basal series that could be added to the request.

3. Mixed timezones. The prompt mandates timestamps as `yyyy-MM-dd HH:mm:ss.SSSZ` (UTC), but hourly trends use the browser's local `getHours()` (~line 532), event times are built with `toLocaleString` with no zone marker, and settings segments are matched by local hour. Nothing in the prompt states the user's offset. In our study the package carried the same data keyed in both UTC and local time and 30 of 490 model conversations placed the overnight low pattern at the wrong clock hour. Suggest one timezone throughout, stated explicitly in the prompt.

4. Asserted premises. The prompt states as fact how SmartAdjust weights 48-72h TDI and a "2-hour DIA constraint". The model will echo these rather than verify them (we saw the same with textbook priors), so any inaccuracy in the persona becomes an inaccuracy in every audit. Consider phrasing these as things to verify during the research phase rather than givens.

## Design consideration: answer variability

This is not a bug in your code, it is a property of the mechanism, but it is worth a README warning. We replayed a near-identical copy-paste workflow 50 times per model against eleven models on one fixed record: the models read the data accurately (96.8-100% of quoted figures verified) and still returned materially different recommendations run to run and model to model, e.g. one model proposed eighteen different pairs of safety limits across fifty runs on identical input. Your workflow adds two further variance sources on top of sampling: the mandatory web-research phase, and the model-chosen 48-72h "Critical Interest Window" which redirects everything downstream. A user who runs the audit once has no way to know which draw they got. Two cheap mitigations: recommend in the README that users run the triage two or three times and compare before acting on anything, and consider asking the model to state its confidence per finding rather than deliver a single authoritative audit. The study (490 conversations, all transcripts public) is in submission; happy to share the preprint and data.

Also, genuine credit for the "turn off chat training before pasting" warning in the README. Almost nothing in this space says that, and it matters.
